# Better Auth server implementation review

Date: 25 October 2026.

This implements the server foundation from [the approved design](02-design.md). `AUTH_PROVIDER` defaults to `clerk`; no environment was switched, no UI was changed, and no reset or deployment occurred. Better Auth is not ready for cutover. The user subsequently approved applying the additive migration to the configured development Neon database; it is now applied, with Clerk still active.

## Implemented boundary

- `packages/auth/adapters/better-auth-server.ts` lazily constructs Better Auth 1.7.12 with the PostgreSQL Prisma adapter and `transaction: true`. It uses `systemDatabase`, the existing owner connection from `DATABASE_URL`, as explicitly requested for this task. It never uses `DATABASE_APP_URL` or a tenant transaction. The separate restricted auth role in the design remains later hardening work.
- The eight neutral helpers select Clerk or Better Auth without a fallback between providers. Better Auth re-reads session, membership, role and Account readiness. Expected account denial fails closed; operational errors propagate. Native permission checks require `success === true` in addition to the fixed local statements.
- The organisation plugin uses `createAccessControl` and the existing statements, four roles, creator role `owner`, disabled teams and disabled dynamic roles. The complete permission matrix tests every action for each role, including the preserved viewer/direct-manager grant and owner-only ownership/company-removal actions.
- Google and multi-tenant Microsoft use built-in providers, with Microsoft tenant `organizations`. Xero uses `genericOAuth`, provider `xero-auth`, verified OIDC discovery, PKCE, HTTP Basic client authentication and exactly `openid profile email`. It only receives `XERO_AUTH_CLIENT_ID` and `XERO_AUTH_CLIENT_SECRET`. Configuration rejects either identity credential matching either payroll credential.
- Email/password requires verified email and a 12 to 128 character password. Verification and password recovery expire after one hour. Password reset revokes sessions; password change forces other-session revocation. Magic links are hashed, single-use and expire after five minutes. All mail callbacks use `packages/email`; transport failures propagate without disclosing links.
- Sessions expire after seven days, update daily and have a one-day freshness requirement. Cookie caching is disabled. Cookies are HttpOnly and SameSite=Lax, Secure on HTTPS including Preview. Only the exact production app origin enables the `teamcalendar.online` parent domain. Local and Preview use host-only cookies with separate HTTP-development names.
- Implicit linking is disabled, trusted-provider bypasses are empty and different-email linking is forbidden. Both local and incoming email verification, matching identities and a fresh session are checked again during redirect linking. Direct ID-token linking is denied because the pinned native relink branch can return before checking incoming email verification.
- The native HTTP limiter uses database storage and atomic adapter operations, with explicit sign-in, magic-link and recovery limits. The custom auth-context resolver has a separate atomic PostgreSQL bucket, 100 requests/minute per trusted Vercel address, with one shared development/unknown-address bucket. API egress sharing this bucket needs load verification before release.
- `dash()` from `@better-auth/infra` 0.4.22 is omitted unless `BETTER_AUTH_INFRA_ENABLED=true` and its private key is supplied. Activity tracking and managed directory sync are disabled. `nextCookies()` is last. Core telemetry is disabled. The design's residency and administrative-data review still blocks enabling Infrastructure.

The catch-all route mounts repository handlers through `toNextJsHandler` inside `packages/auth`, preserving the provider import boundary. Explicit HTTP path and JSON field allowlists remove session bearer values and credential data while preserving redirects and Set-Cookie. Organisation reads currently stay server-only; user/Account deletion and unproved lifecycle writes are closed.

## API transport

The approved transport is online cookie validation, not JWT/JWKS or the bearer plugin. There is no JWKS table. The API uses `AUTH_CONTEXT_MODE=remote`; the app uses `local`. API requests forward only the configured session cookie to the fixed paired app's `/api/auth-context` endpoint. The response contains safe user/session/permission fields and expiry, with no token. Redirects are rejected, errors propagate, and refreshed cookies retain their response path. Protected API mutations require the exact app Origin; credentialed CORS and preflight allow only that app.

Local origins are `http://localhost:3000` and `http://localhost:3002`. Production origins are `https://app.teamcalendar.online` and `https://api.teamcalendar.online`. Preview validates an explicit candidate pair and keeps the cookie on the app host. Browser proxy routes, Preview SSE/payroll OAuth routing and UI adoption remain later work. Existing screens and their Clerk client wrappers have not been switched.

## Generated storage and migration

The pinned Better Auth CLI generated eight mapped models; repository extensions add the ninth audit model, timestamps, UUID relationships, fixed role/status enums and identity/membership uniqueness. Shared field mappings are in `packages/auth/better-auth-schema.ts`.

Migration: `packages/database/prisma/migrations/20261025120000_better_auth_server/migration.sql`, generated with Prisma 7.10.1 from the before/after schemas. It adds nine tables, three enums and ten foreign keys. It contains no drop, reset or mutation of existing domain tables. No `db push` was used. All 43 migration checksums now match the development database, and Prisma reports no schema differences. Postgres introspects the UUID default as `gen_random_uuid()`; the Prisma schema uses that canonical spelling to avoid false drift. The applied migration retains its original, checksum-verified `pg_catalog.gen_random_uuid()` SQL.

Tables: `auth_users`, `auth_sessions`, `auth_identities`, `auth_verifications`, `accounts`, `account_members`, `account_invitations`, `auth_rate_limits`, `auth_audit_events`. No app-role grants are added. Existing domain account/user columns remain text and retain Clerk data. Converting them to UUID auth foreign keys requires the approved clean-reset cutover; there is no ID remap or fabricated backfill. Release fixture cleanup keeps auth/control UUID ownership separate from Clerk-era domain fixture ownership.

CLI evidence is retained privately in `.cache/better-auth-schema`: `generated.prisma` is the CLI output, `auth.ts` is its schema-only configuration, and `before.prisma` is the migration input snapshot. Commands used the pinned `auth@1.7.12` CLI and Prisma's `migrate diff --from-schema ... --to-schema ... --script --output ...`. The native `auth check schema` also passed against the generated Prisma client. This schema check does not establish live database behaviour.

## Deliberate cutover gates

Public signup and organisation/membership lifecycle mutation are disabled, including direct server API writes, while atomic admission/bootstrap and controlled lifecycle enforcement remain unproved. `databaseHooks.user.create.before` also rejects creation, so an OAuth or magic-link signup cannot commit a membership-less user through another native path. Prepared test identities can exercise sign-in. This is a closed server foundation, not a completed signup or onboarding implementation.

Before opening these paths, implement and prove admitted-owner/invitation bootstrap, default payroll company provisioning, country/timezone validation, final-owner/final-membership database protection, transactional target-session revocation, Person linking and the local audit writer. The audit table is reserved storage, not a working audit trail. Better Auth native hooks alone do not establish these invariants. The account directory/admin facade, background identity queries and existing Clerk webhook shutdown also remain coordinated cutover work.
