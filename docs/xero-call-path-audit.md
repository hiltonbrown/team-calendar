# Xero call-path audit

This inventory covers the repository's Xero routes, server actions, background jobs, regional provider helpers, credential lifecycle operations and test/release tooling. It records source inspection of the shared-connection model: customer access starts with a local `XeroConnection` resolved by both `clerk_org_id` and `organisation_id`; its canonical `XeroAuthorisation` owns credentials. The connecting Clerk user is an OAuth initiator and audit actor, not the identity used to resolve subsequent payroll access. `xero_user_id` is the verified provider principal.

**Compliant means the inspected source follows the Organisation scope, canonical credential and current-token dispatch contract. It does not assert successful database integration, live provider execution or deployment.** Database integration remains unverified: the targeted local integration attempts failed in fixture cleanup at `database.auditEvent.deleteMany()` before test bodies executed. Mocked unit tests establish service behavior at their stated boundaries, not PostgreSQL behavior.

## Findings and implementation status

The original payroll dispatch helpers could retain a resolved token across rate-limit waits, pages or retries. The fix threads `accessContext` through every AU/NZ/UK payroll read and AU write. `xeroFetch` re-resolves the scoped current canonical connection after admission and before each HTTP attempt, verifies tenant/region/header consistency, and replaces the bearer. Auth recovery tracks the bearer actually dispatched. Source inspection confirms these changes; it does not establish live provider or database behavior.

The canonical resolver has also been hardened to use the final current grant for capability/expiry validation, token decryption and provider capture, with safe Result errors for unreadable credentials. This addresses shared-grant rotation between the initial and final scoped reads.

Provider-connection inventory verification now supplies the same scoped transport context, so its bearer is re-resolved after rate-limit admission. Its captured-version compare-and-set remains conservative if a concurrent refresh changes the grant. Disconnect retains its synchronous remote-first lifecycle: canonical access is resolved first, then the current scoped credential is read under the existing authorisation and connection locks. Those locks remain held through remote dispatch and local teardown, so another execution cannot rotate that grant during the call. A second transport refresh inside that lock would be redundant and could attempt to reacquire the same grant lock.

OAuth bootstrap necessarily precedes creation of a connection. Signed state and the authenticated, short-lived Organisation-bound session supply its authority; Xero inventory supplies the selectable tenant IDs. Pending selection supplies an Organisation/session-bound dispatch callback that reloads canonical status, capabilities and expiry after rate-limit admission on every attempt, including retries. The callback is restricted to GET /connections and GET /api.xro/2.0/Organisation; it cannot authorise payroll endpoints. Any refresh delegates to the existing central implementation. Code/refresh/JWKS and connection-inventory endpoints do not take a payroll tenant header. Encryption maintenance requires decryption of the canonical grant to rewrite its encrypted envelope and makes no payroll API call.

No additional production path was found that resolves customer credentials through the original app user, trusts an unchecked browser Xero tenant, or stores token copies in a Person, OAuth session or connection. This is a source finding, not an assertion that all integrations have passed. Real PostgreSQL integration remains unverified until fixture setup and the relevant service/job suites execute successfully.
